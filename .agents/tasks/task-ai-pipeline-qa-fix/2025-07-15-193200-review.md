# AI pipeline fixes v2: timeout alignment, CORS locality, and unknown-intent routing

The five v1 issues have been addressed. The CORS race condition is fixed — `corsHeaders(req)` is now a `const` local inside `Deno.serve`, and `json()` is a local closure that captures it. The client/server timeout gap is closed: brain.ts uses 28s, above the server's 25s + network overhead. The `_shared/llm.ts` Gemini timeout is now aligned at 25s. The `gemini-3.6-flash` model name is confirmed valid by the user.

Two new concerns emerged during this pass. The `tooManyRequests()` helper and the `checkAndConsumeCredit()` module build their own responses with static CORS headers (hardcoded origin), bypassing the per-request CORS that `proxy-ai` now computes correctly — if the browser hits from `localhost:5173` in dev, 429 and credit-exhausted responses will be CORS-blocked. The new unknown-intent branch in OraculoBar lacks a try-catch, so an unhandled rejection leaves the spinner in `busy` state permanently.

Watch for: **Static CORS in shared helpers** — `tooManyRequests()` and `iaCredits.ts` bypass the per-request origin reflection, causing CORS failures for non-production origins on error paths (confirmed). **Unguarded async in OraculoBar** — the unknown branch has no try-catch; a thrown error leaves `setBusy(true)` stuck forever (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Two shared helpers (`tooManyRequests` in `rateLimit.ts` and the 429 response in `iaCredits.ts`) still construct responses with a static `Access-Control-Allow-Origin` hardcoded to the production URL. These are called from within the handler *after* the local CORS was computed, so their responses won't match the request origin in dev environments — making rate-limit and credit-exhaustion paths untestable locally and broken for any non-production origin.

The OraculoBar's new unknown-intent branch calls `askOmicron` without a try-catch. The `coach` branch had the same pattern pre-existing, but the unknown branch is the catch-all — every unrecognized input hits it. A thrown error leaves the UI in a permanent loading state with no recovery.

The `error: 'ai_unavailable'` field added to brain.ts is dead code — no consumer reads it. The distinction between a real AI response and a canned offline fallback is invisible to the UI.

## CORS bypass in shared error responses

The `proxy-ai` handler computes per-request CORS correctly, but two code paths return responses that bypass it:

```typescript
// rateLimit.ts — tooManyRequests()
headers: {
  "Access-Control-Allow-Origin": Deno.env.get('PUBLIC_SITE_URL') || "https://sistema-omicrom.vercel.app",
  ...
}

// iaCredits.ts — checkAndConsumeCredit()
const CORS = {
  'Access-Control-Allow-Origin': Deno.env.get('PUBLIC_SITE_URL') || 'https://sistema-omicrom.vercel.app',
  ...
};
```

When a dev hits the function from `localhost:5173`, the success path returns `Access-Control-Allow-Origin: http://localhost:5173` (from `corsHeaders(req)`), but a rate-limit or credit-exhausted response returns `Access-Control-Allow-Origin: https://sistema-omicrom.vercel.app`. The browser sees the mismatch and blocks the response — the client's `supabase.functions.invoke()` throws a network error instead of receiving the structured 429 JSON. In production this doesn't manifest because the origin matches, but it makes rate-limit and credit behavior untestable locally and creates a silent failure mode for any future allowed origin.

The fix is to pass the computed `cors` object into both helpers, or restructure them to return data and let the caller build the Response.

## OraculoBar: unguarded await on the catch-all path

```typescript
setBusy(true);
flash('oraculo', 'Déjame pensar…', 20000);
const r = await askOmicron(text, { ... });
setBusy(false);
```

`askOmicron` has an internal try-catch and returns a fallback on failure, so under normal conditions this won't throw. But if `profile` is unexpectedly null in a way that causes a property-access error during context construction, or if a future refactor removes brain's internal catch, `setBusy(false)` is never reached. The microphone button stays in its pulsing animation state with no recovery path short of a page reload.
