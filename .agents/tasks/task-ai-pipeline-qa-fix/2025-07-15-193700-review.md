# AI pipeline QA fixes: timeout, CORS, guest access, and unknown-intent routing (v3)

Ten bugs preventing AI from responding to users are fixed. The client timeout now uses a working Promise.race pattern, CORS is computed per-request as a local const (no race conditions), shared error helpers accept a CORS override (no mismatch on dev origins), the guest credit bypass is intentional, the unknown-intent path in OraculoBar routes to the AI brain wrapped in try-catch-finally, and timeouts are aligned (25s server, 28s client). All concerns from v1 and v2 have been addressed.

Watch for: **Coach branch in OraculoBar lacks try-catch** — unlike the fixed unknown branch, the coach branch still has bare `await askOmicron()` without error handling, leaving `setBusy(true)` stuck on failure (confirmed, but pre-existing code — not modified in this diff). **Client-side rate limit never enforced** — `checkOmicronLimit()` is exported but never called by any consumer; the only gate is the server-side 15 req/min IP limit (confirmed).

**Verdict**: APPROVED

## High-level view

The CORS fix is complete: per-request computation as a local `const`, captured by the `json()` closure, and passed through to `tooManyRequests()` and `checkAndConsumeCredit()` via the new `corsOverride` parameter. Static fallbacks in both helpers preserve backward compatibility for callers that don't pass it.

The timeout chain runs Gemini abort at 25s → proxy-ai returns → client Promise.race at 28s. The 3s margin accommodates network overhead without the client discarding valid slow responses.

The pre-existing coach branch in OraculoBar has the same unguarded `await askOmicron()` pattern that was fixed in the unknown branch. It wasn't modified in this diff and is out of scope, but the asymmetry is worth a follow-up.

`checkOmicronLimit()` and `getRemainingCredits()` in `brain.ts` are dead code — exported but never called. The real protection is server-side only.

## Coach branch asymmetry with the fixed unknown branch

The unknown-intent code path was correctly wrapped:

```typescript
// unknown branch — fixed in this PR
try {
  const r = await askOmicron(text, { ... });
  // ...
} catch (err) {
  // error flash
} finally {
  setBusy(false);
}
```

The coach branch (lines 154–172) uses a simpler pattern that predates this PR:

```typescript
// coach branch — pre-existing, unchanged
setBusy(true);
const r = await askOmicron(text, { ... });
setBusy(false);
```

A property-access error during context object construction (e.g., `profile` becoming `null` between the check and the destructure) or a future refactor removing brain's internal catch would leave the UI stuck in loading state with no recovery. The failure mode is identical to what the unknown branch just fixed — `setBusy(true)` persists, the microphone button pulses indefinitely.

## Unused client-side rate limit

`brain.ts` exports `checkOmicronLimit()` and `getRemainingCredits()`, both reading from localStorage with a 20/day cap. Neither is called anywhere in the codebase. The actual protection layers are:

- Server-side: 15 requests/min per IP (via `checkRateLimit` in proxy-ai)
- Server-side: per-user credit system for authenticated users (via `checkAndConsumeCredit`)
- Guest bypass: unlimited calls gated only by the IP rate limit (intentional per v1 discussion)

If server-side limits are the source of truth, the dead functions should be removed to avoid misleading future developers into thinking client-side limits are enforced.
