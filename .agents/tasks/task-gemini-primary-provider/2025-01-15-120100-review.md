# Gemini-first LLM provider with browser TTS fallback (v2)

This change promotes Google Gemini (gemini-2.0-flash) as the primary LLM provider across all Supabase Edge Functions, with OpenRouter demoted to a 6-model fallback chain. A shared `_shared/llm.ts` module encapsulates the two-tier strategy for 9 domain functions, while `proxy-ai` keeps its own inline Gemini path (it has additional concerns: user-supplied temperature, dead-model caching, credit gating). The frontend `voice.ts` gains a browser speechSynthesis fallback when proxy-tts signals all TTS models failed.

The v1 review raised 5 issues — all addressed in commit 526e9a9: API key moved to header, 22s timeout added to `_shared/llm.ts`, `{ once: true }` on abort listeners, maxTokens/temperature clamped in the shared module, and OpenRouter fallback expanded to 6 models.

Watch for: `proxy-ai`'s Gemini fetch still has no timeout — the fix was applied to `_shared/llm.ts` but not to the duplicated inline path (confirmed). The shared module's temperature is hardcoded at 0.7 via a no-op clamp expression that appears to be a copy-paste artifact (confirmed, low severity). The `openrouter.backup.ts` dead file remains in the tree (confirmed, cosmetic).

**Verdict**: NEEDS_CHANGES

## High-level view

The `proxy-ai` Gemini call was the only code path that didn't get a timeout in the fix commit. It already has a 25s AbortController on its OpenRouter calls, so the pattern is established — the Gemini path was simply missed. A stalled Gemini connection would block the entire request until Supabase's global function timeout (default 60s) kills it, leaving the user waiting with no fallback attempt.

The shared `_shared/llm.ts` has a dead expression `Math.min(Math.max(0.7, 0), 1.5)` where `0.7` should arguably be the `temperature` parameter — except `callLLM` doesn't expose temperature at all. The expression evaluates to a constant and the clamp logic is vestigial. If callers ever need tunable temperature, the function signature would need a parameter; for now it's just confusing dead math.

The `openrouter.backup.ts` file is unreferenced dead code. It won't cause runtime issues but adds noise to the shared directory.

## Missing timeout on proxy-ai's Gemini path

The fix commit (526e9a9) added a 22s AbortController to `_shared/llm.ts`'s `callGemini` but left `proxy-ai`'s inline Gemini block untouched:

```typescript
// proxy-ai/index.ts — no abort controller
const geminiResp = await fetch(GEMINI_URL, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'x-goog-api-key': GEMINI_KEY,
  },
  body: JSON.stringify(geminiBody),
});
```

Contrast with `_shared/llm.ts`:

```typescript
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), 22000);
const resp = await fetch(GEMINI_URL, { ..., signal: controller.signal });
clearTimeout(timer);
```

`proxy-ai` is the user-facing chat endpoint — arguably the most important one to protect from hangs. Without a timeout, a stalled Gemini TCP connection blocks the entire request for up to 60s (Supabase's default function timeout) before the user sees a failure. The OpenRouter fallback never gets a chance.

## Hardcoded temperature in shared module

`_shared/llm.ts` uses this expression in both `callGemini` and `callOpenRouter`:

```typescript
temperature: Math.min(Math.max(0.7, 0), 1.5)
```

This always evaluates to `0.7`. The clamp logic (`Math.min(Math.max(x, 0), 1.5)`) makes sense when `x` is a variable (as in `proxy-ai` where it's `temperature` from the request), but here `0.7` is a literal. The code reads as if it's clamping a parameter but isn't. Since `callLLM` doesn't accept a temperature argument, this is intentionally fixed at 0.7 — the clamp wrapper is misleading dead code. Low severity, but worth simplifying to `temperature: 0.7` to avoid suggesting the code does more than it does.
