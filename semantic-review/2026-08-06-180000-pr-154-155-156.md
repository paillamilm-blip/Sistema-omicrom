# Conversational robustness + CV-driven synergy nodes + documentation unification

Three PRs land together: #154 hardens the OmicronAssistant conversational flow (context-aware coach/tutor calls, a safety timeout, a profile-load guard on greeting, and a global try/catch). #155 replaces the flat 70% node levels with real AI-analyzed percentages, adds synergy detection between related skills, and introduces a new orbital profile view (`PerfilSkillVisual`). #156 collapses 12 documentation files into 8 by merging redundant content.

Watch for: The greeting `useEffect` can fire with a stale `top` if `profile` arrives truthy before `gemelo` loads (confirmed). OrbShell's `handleNodeTap` hijacks the "Inicio" hub for all users with skills, blocking normal Perfil tab navigation (confirmed). The OrbShell fallback for unknown intents is a static help message instead of calling the Tutor IA like OmicronAssistant does (confirmed behavioral inconsistency). A stale reference to `VISION_OMICROM.md` persists in `.kiro/steering/vision-producto.md` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

PR #154 wraps every branch of `handleQuery` in a try/catch with a 15-second safety timeout that auto-resets the "thinking" state. The greeting race-condition fix introduces a subtlety: if `profile` loads before `top` (derived from `computeSteps(profile, gemelo)`) is recalculated, the greeting fires once with stale data and never re-fires.

PR #155 replaces the hardcoded 0.7 node level with a `pctMap` lookup from `skills_detail`, and adds a synergy bonus of +8% when 2+ skills from the same thematic group coexist. The `handleNodeTap` override on the "Inicio" node bypasses normal navigation for any user who has at least one skill, with no way to reach the Perfil tab from that hub without typing a command.

PR #156's documentation merge is clean in the source `.md` files but leaves a dangling reference in `.kiro/steering/vision-producto.md`, which could mislead future AI-assisted sessions.

## Greeting race: profile loads before gemelo

The greeting `useEffect` in OmicronAssistant guards on `profile` being truthy, then immediately sets `greetedRef.current = true` and uses `top`. The dependency array is `[profile, top, omicronSay]`.

```
Render 1: profile = null, top = null → early return (profile guard)
Render 2: profile = {...}, gemelo = null → top = null
           greetedRef set to true, greeting fires with fallback message
Render 3: gemelo loads → top = { title: '...', why: '...' }
           but greetedRef is already true, greeting never re-fires
```

The greeting always uses the "no gemelo" fallback for users whose profile resolves faster than the gemelo data. A minimal fix: also guard on `gemelo !== undefined` if the intent is to show the personalized next-step push.

## Behavioral divergence between OrbShell and OmicronAssistant

Both components process text through `interpret()` from `oraculo.ts`, but handle results differently:

| Intent     | OmicronAssistant                        | OrbShell                          |
|------------|-----------------------------------------|-----------------------------------|
| `navigate` | Calls `omicronSay` + sets tab           | Selects node + opens preview      |
| `coach`    | Calls `askCoach(coachCtx)` with context | Calls `askCoach(coachCtx)` same   |
| `unknown`  | Calls `askTutor(text, coachCtx)` (AI)   | Static help string (no AI call)   |

The `unknown` divergence is the most impactful: the OrbShell input bar is the primary interaction point in the orb-centric UI, yet it can't answer free-form questions. A user typing "how do I improve my quality score?" gets a canned response instead of an AI answer.

OrbShell's `handleTextInput` also has no try/catch or safety timeout. If `askCoach` throws (network failure, function not deployed), the promise rejection is unhandled and no error feedback reaches the user.

## handleNodeTap hijack on "Inicio"

```tsx
const handleNodeTap = useCallback((node: OrbNode) => {
  const userSkills: string[] = sbProfile?.skills ?? [];
  if (node.id === 'inicio' && userSkills.length > 0) {
    setShowProfileVisual(true);
    return; // ← never reaches preview/fullscreen flow
  }
  setSelectedNode(node);
  setState('preview');
  setActiveTab(node.tab);
}, [setActiveTab, sbProfile]);
```

Once a user has uploaded their CV (even one skill detected), the central "Inicio" node always opens the PerfilSkillVisual overlay. The Perfil/Inicio tab content (profile card, CV convalidation button, dossier view) becomes unreachable from the orb without typing a text command. This is a UX regression for the most important navigation path in the app.

## buildSkillNodes: synergy cross-contamination

The synergy bonus applies +8% when 2+ skills substring-match within a group. The edge case: a user with skills `["Google Analytics", "Data Visualization", "Marketing Digital"]`. The substring `"analytics"` is in the Python/ML group, and `"data"` also matches. The ML group activates (2 matches), giving a false synergy bonus to business-oriented skills.

Separately, the `pctMap` lookup uses exact `skill.toLowerCase()` matching against `skills_detail[].name.toLowerCase()`. If the `skills` array stores `"React.js"` but `skills_detail` stores `{ name: "React", pct: 85 }`, the lookup misses and falls back to 0.7 — silently hiding the AI's actual analysis.

## PerfilSkillVisual: missing focus trap and screen reader semantics

The component renders a fixed-position overlay (`zIndex: 9999`) but:

- The orbital visualization (animated rings, glowing dots) has no `aria-hidden` or `role="presentation"`. Screen readers announce empty motion containers.
- There is no focus trap. When the overlay opens, keyboard focus stays behind it and tab navigation reaches elements underneath.
- No focus is moved into the overlay on open, violating WCAG 2.4.3 (Focus Order) for modal-like content.
