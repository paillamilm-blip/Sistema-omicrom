# Full session refactor: 2-concept architecture, Motion System, Jarvis Presence, 17 bug fixes

This session restructured the entire Sistema Ómicron codebase around a 2-concept model (Ómicron = coach that pushes you, Gemelo = your digital twin that measures you). The `features/perfil/` module was deleted and its contents merged into `features/gemelo/`. A circular dependency between gemelo and omicron was broken by extracting pure guidance functions into `shared/utils/guidance.ts`. On top of the structural refactor, 12 motion components (`shared/motion/`), a spatial audio system, an emotion-aware ambient UI, and three innovations (AmbientDrone, ProgressiveBlur, GemeloAging) were added. All 9 feature modules were wired to use the new systems.

Watch for: **TypeScript compiles cleanly** — the only error is a pre-existing `react-router-dom` type reference in an unused utility file (not introduced by this session). **No dangling imports remain** (confirmed). **No circular dependencies** (confirmed — gemelo/ never imports from omicron/). The `CelebrationBurst` component creates 28 particle objects via `setParticles` per animation frame — on budget devices this could cause GC pressure during the ~1.4s burst (possible).

**Verdict**: APPROVED

## High-level view

The architectural refactor is clean and complete. The `features/perfil/` directory no longer exists, all its components and services live in `features/gemelo/`, and every cross-module import that previously pointed at `perfil/` now resolves to the correct `gemelo/` path (confirmed by grep and TypeScript compilation). The circular dependency between gemelo and omicron is broken: `shared/utils/guidance.ts` holds the pure functions both modules need, and `gemelo/` never imports from `omicron/`.

The `SelfManagedPulseBar` pattern (module-level setter callback) avoids re-render propagation that was flagged in a previous review — the pulse state is self-contained and doesn't flow through the component tree. The `EmotionProvider` injects CSS custom properties directly on `document.documentElement` — consumer components read vars from CSS, not React context re-renders.

All audio invocations are in event handlers or post-async success paths (never in render or effects). The AmbientDrone reuses the shared AudioContext singleton to avoid hitting the iOS 6-context limit, and receives state changes only via a dedicated `DroneSync` child component with `useEffect`.

All decorative elements (particles, aura backgrounds, pulse bar, glow overlays) carry `aria-hidden="true"`. Every motion component respects `prefers-reduced-motion` via both the `useReducedMotion` hook and CSS media queries. The audio system auto-mutes when reduced motion is preferred.

<summary>Issues (3)</summary>

1. **CelebrationBurst GC pressure on low-end devices** — The animation loop calls `setParticles(prev => prev.map(...))` every frame for 1.4 seconds, creating 28 new objects per frame (~84 frames × 28 = ~2352 object allocations). On budget Android devices this could trigger minor GC pauses. Consider using a ref + requestAnimationFrame with direct DOM manipulation for particle positions instead of React state. (possible — would need profiling to confirm)
2. **EmotionParticles uses Math.random() in render** — The 8 particle positions are generated with `Math.random()` directly in the render body, meaning they shift on every re-render. In practice this only triggers on emotion state changes (rare), but if a parent re-render propagates, particles visually jump. Memoize the random values or move generation to a ref. (possible — only matters if parent re-renders frequently)
3. **`useProgressiveBlur` timer race on rapid unmount/remount** — The `timersRef.current.push(t2)` inside the inner setTimeout can push to a stale ref array if the component unmounts between `t1` firing and `t2` being created. The cleanup only calls `timersRef.current.forEach(clearTimeout)` on unmount, but `t2` hasn't been pushed yet at that point. In practice, the 300ms + 600ms delay makes this extremely unlikely in normal navigation. (possible)

## CelebrationBurst allocation pattern

```tsx
function tick(now: number) {
  setParticles(prev => prev.map(p => ({
    ...p,
    x: p.x + p.vx,
    y: p.y + p.vy,
    vy: p.vy + 0.15,
    rotation: p.rotation + p.rotationSpeed,
    opacity: 1 - progress,
  })));
  rafRef.current = requestAnimationFrame(tick);
}
```

Each frame creates 28 new particle objects via spread. At 60fps over 1.4s that's ~2352 allocations. On modern devices this is invisible. On budget Android (Snapdragon 4-series, 3GB RAM) the V8 young-generation GC may hiccup for 1-2ms. The component is used only on quiz pass — not in a hot path. This is an optimization opportunity, not a blocking issue.
