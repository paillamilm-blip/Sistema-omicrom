# Merge perfil/ into gemelo/ — 2-concept architecture refactor

The diff consolidates the previously split `features/perfil/` module entirely into `features/gemelo/`, reducing the system's conceptual surface from three overlapping modules (omicron + perfil + gemelo) to two with clear responsibilities: Ómicron as the active coach, Gemelo as the passive identity layer. Twenty components, three services, and one hook physically move; the circular dependency between gemelo and omicron is broken by extracting `nodeGuidance` and `levelInfo` into `shared/utils/guidance.ts`. Import paths across 30+ files are updated, the `TabId` value `'perfil'` continues to resolve correctly to the renamed `GemeloTab`, and architecture documentation is added as Section 8 of `DEFINICION_OMICROM.md`.

Watch for: gemelo's `RedSocialTab` still imports UI chrome directly from `features/omicron/components/OmicronChrome` — this is a presentation-layer cross-reference, not a service-level cycle, but it prevents gemelo from being independently testable without omicron (confirmed). A stale documentation reference in `DEFINICION_REPUTACION_OMICROM.md` still points to the deleted `src/services/reputationService.ts` path (confirmed).

**Verdict**: APPROVED

## High-level view

The circular dependency is cleanly severed. `shared/utils/guidance.ts` contains two pure functions (`levelInfo`, `nodeGuidance`) that depend only on `@/types` — no feature-module imports. Both gemelo's `Guidance.tsx` and omicron's `coach.ts` now import from this neutral location, and `coach.ts` re-exports the symbols so existing consumers of `nodeGuidance` via `@/features/omicron/services/coach` continue to resolve without code changes. The dependency graph is now unidirectional: omicron → shared ← gemelo, with no gemelo → omicron service-level edges.

The `TabId` value `'perfil'` is deliberately preserved at the routing layer. `OrbShell.tsx` maps `case 'perfil'` to `<GemeloTab />`, `preload.ts` maps `perfil` to the `GemeloTab` chunk, and the `HUB_NODES` array keeps `tab: 'perfil'` for the "Mi ADN" node. Deep links, analytics events, and state serialization continue to work without a migration of stored `TabId` values.

There is one remaining cross-module UI import: gemelo's `RedSocialTab.tsx` imports `OmicronChrome` (layout primitives like `oc`, `OmicronHeader`). This is an app-wide shared layout convention used by every tab in the system (academia, chat, empleos, market, wallet, gobernanza all do the same), so it's a deliberate presentation pattern rather than an architectural dependency. It could be promoted to `shared/` in the future but is not a regression introduced by this refactor.

## Circular dependency resolution via `shared/utils/guidance.ts`

The previous cycle was: `gemelo/Guidance.tsx` imported `nodeGuidance` from `omicron/services/coach.ts`, while `omicron/OrbShell.tsx` imported `useGemeloProfile` and other gemelo services. Extracting the two pure functions into `shared/utils/guidance.ts` breaks the cycle because `shared/` has no feature-module dependencies — it imports only from `@/types`:

```typescript
import type { TabId, Profile, GemeloDigital } from '@/types';
export function levelInfo(pe: number) { ... }
export function nodeGuidance(tab: TabId, ...) { ... }
```

The re-export in `coach.ts` (`export { levelInfo, nodeGuidance } from '@/shared/utils/guidance'`) is safe for tree-shaking: bundlers (Vite/Rollup) trace named re-exports through to the original module. Any consumer that imports only `computeSteps` from `coach.ts` will not pull in guidance functions, and vice versa.

## Import completeness — no dangling references

A grep for `features/perfil` across all `.ts` and `.tsx` files returns zero matches. The same for `@/hooks/useGemeloProfile` (old path) and `@/services/reputationService` (old path) in source code. The only surviving reference to the old path is in `DEFINICION_REPUTACION_OMICROM.md` line 178, which still says `src/services/reputationService.ts`. Documentation-only gap — no build or runtime impact — but it will confuse anyone reading the doc as a code map.

## Module boundary assessment

Post-refactor dependency graph for the two concepts:

```
shared/utils/guidance.ts   (pure, no feature imports)
        ↑            ↑
   omicron/          gemelo/
   services/         components/Guidance.tsx
   coach.ts

omicron/OrbShell  →  gemelo/hooks/useGemeloProfile
                 →  gemelo/services/progressive
                 →  gemelo/services/proactive

gemelo/RedSocialTab  →  omicron/components/OmicronChrome  (UI layout only)
```

The omicron → gemelo direction is legitimate (the coach reads identity data). The gemelo → omicron edge is presentation-only (`OmicronChrome` exports layout primitives used by every tab). No gemelo service imports any omicron service, which is the boundary that matters for testability and circular-dependency freedom.

## Test coverage gap

The `GemeloTab` component has no unit/integration test. The rename from `PerfilTab` to `GemeloTab` means the lazy-import path (`import('@/features/gemelo/components/GemeloTab').then(m => ({ default: m.GemeloTab }))`) is validated only by TypeScript's type checker, not by an actual load test. Pre-existing gap, not introduced by this PR.
